Protocol v1 · in security review

Your secrets sync. The server only sees ciphertext.

ak-vault is the opt-in, end-to-end encrypted sync layer for AgentKit's ak secrets. Secrets are sealed on your device before they leave it, agents keep reading from the local vault, and with sync off nothing touches the network.

See how it works Start with the local vault

Cloud sync is not generally available. The production sync API is live as a pre-release preview, by owner decision, before the owner's security review, which is not an independent third-party review: anyone signed in to AgentKit who runs the preview ak secrets sync commands can use it. Do not put production credentials in it yet. The local ak secrets vault works today without it.

The problem

Secrets drift into places they were never meant to be.

A key starts in one .env file. Then it is pasted into a chat for a teammate, lands in shell history, gets copied to a second laptop and ends up in an agent's config. Every copy is plaintext that someone else can read.

Values live in the OS keychain or the age-encrypted file vault. Agents receive a value only through a grant you approved, and every release is recorded in a local audit ledger.

That fixes one machine. ak-vault adds the missing piece: the same vault on your other devices, without handing the values to a server.

How sync works

Sealed on one device. Relayed as ciphertext. Verified on the next.

Your local vault stays the source of truth. Sync is an optional path between devices you enrolled yourself.

Promises and fine print

Every promise comes with its fine print.

These are design properties of protocol v1 as proposed. They hold only after the implementation passes the security gate in issue #8 and the owner's review signs off (not an independent third-party review).

Design propertyLimitation
GuaranteeEncrypted before upload

Values, names, descriptions, tags, profiles, policy and audit entries are sealed on the device. spec §3.2, §7

LimitationMetadata is visible

Random IDs, revisions, sizes, timestamps, device public keys, roles and request metadata.

GuaranteeOwner-signed membership

A hash-chained, owner-signed log decides which devices receive the vault key. Injected recipients are rejected. spec §4

LimitationOne key per vault

Anyone holding a vault's key can decrypt every item in it. There is no per-secret access; use separate vaults instead.

GuaranteeRollback detection

Devices keep signed checkpoints and refuse server state older than one they already witnessed. spec §6

LimitationWithheld updates

A malicious server can hide updates that a new or long-offline device has never seen. Detecting that needs a second channel, such as another device's checkpoint.

GuaranteeLive revocation

Device-bound tokens plus a per-request device signature. Revoked devices and sessions are refused on every request, and lookup errors fail closed. spec §9

LimitationNo claw-back

Revocation blocks new keys and ciphertext. Anything a device already decrypted stays exposed, so affected secrets are marked to rotate.

GuaranteeLocal-first and opt-in

resolve reads the local vault and never waits on the Worker. With sync off, secrets make zero network requests.

LimitationPlaintext reaches the child process

ak secrets run (planned) hands the value to the process you approved. The vault controls and records the release; it cannot take the value back from that program.

GuaranteeNo silent overwrites

Writes use revision compare-and-swap. A stale write gets 409 and is kept as a conflict branch for you to resolve, and deleted stays deleted. spec §5

LimitationNot yet reviewed

Protocol v1 is a proposal. Treat every property on this page as a design target until the owner's review signs off.

GuaranteeRecovery without trusting the server

The encrypted recovery bundle carries the owner's public trust anchor, the recovery signing key and the newest witnessed checkpoint, so a fresh device does not take the server's word. spec §3.4

LimitationLose every key, lose the vault

Without an enrolled device, your master password or your recovery key, nobody can decrypt the vault, including AgentKit.

Start

Start local today.

The local vault ships in the AgentKit CLI now. Sync commands are a hidden, unsupported preview in the released CLI; agent-discovery commands are planned and not available yet.

01 available

Import your .env

Move existing values into the vault in one pass. Delete the plaintext file once you have checked the import.

shell
$ ak secrets import-env .env
$ ak secrets list
02 available

Reference, don't paste

Agent configs carry a reference. The value is resolved locally, for an agent you granted it to.

agent config
OPENAI_API_KEY=${secret:OPENAI_API_KEY}
03 preview

Sync a second device

Opt in, then enroll another device by comparing a six-digit code on both screens. Syntax may change.

shell · preview
# PREVIEW: hidden in the released CLI, unsupported, syntax may change
$ ak secrets sync enable

Questions

Questions worth asking a secrets product.

Can I use cloud sync today?

Only as a preview. Protocol v1 is proposed and in security review (#8), and cloud sync is not generally available. By owner decision the production sync API is live before that review as a pre-release preview: if you are signed in and run the preview ak secrets sync commands, your device syncs with it. It is not yet recommended for production credentials. The local ak secrets vault works today.

Can AgentKit read my secrets?

The design says no: the server stores ciphertext and wrapped keys only, and never receives your master password, recovery key or device private keys. It can see the metadata listed under two views of one secret. Treat this as a design claim until the review completes.

What happens if the server is down?

Nothing changes for running agents. resolve reads the local vault and never waits on the network. Changes made while offline sync on the next successful connection, and conflicting edits are kept for you to resolve.

Can I give a teammate access to just one secret?

Not within one vault. A vault key decrypts every item in the vault, so v1 makes no per-secret access claim. Put the secrets you want to share in a separate shared vault.

What if I lose my laptop?

Revoke the device. Revocation is checked on every request, so a revoked device or session is refused new reads and writes. Anything it already decrypted cannot be clawed back, so rotate sensitive credentials at the provider.
