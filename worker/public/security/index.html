Protocol v1 · in security review

Security model, in plain language.

Who ak-vault defends against, how protocol v1 does it, and what remains your risk. This page summarizes the normative protocol v1 specification and threat model; where they differ, they win.

Scope and status

What is being protected

The assets are your secret values and everything that describes them: names, descriptions, tags, profiles, portable policy and the audit trail. All of them are encrypted on your devices before upload. The server keeps ciphertext, wrapped vault keys and the operational metadata it needs to order and authorize writes.

Status: protocol v1 is proposed. It is not approved for production credentials until the security gate in issue #8 records the owner's review sign-off, which is not an independent third-party review. The owner made the production sync API live before that review (an owner waiver, not a sign-off): anyone signed in who runs the preview ak secrets sync commands can use it. It is pre-release and not yet recommended for production credentials.

Out of scope by design: decryption in a web browser, server-held vault keys or KMS, and taking back plaintext that has already been disclosed.

Threat map

Where each attacker sits, and what stops them.

Plaintext exists only inside your devices. Everything that crosses the network or rests on the server is ciphertext, signatures or the listed metadata. Select a marker to jump to its defence.

Adversaries

Threats we design against

Each card pairs the defence in protocol v1 with the risk that stays with you.

1

Malicious or compromised server

Defence in protocol v1
Client-side encryption for everything sensitive; signed records; an owner-signed, hash-chained member list; signed checkpoints that refuse rollback or forks; injected key recipients rejected.
Residual risk
It can withhold updates a new or long-offline device has never witnessed, and it sees operational metadata.
2

Network attacker

Defence in protocol v1
TLS, plus a per-request device signature bound to method, URL, token and body hash, accepted only within a ±60-second window and only once.
Residual risk
Request timing and sizes are observable.
3

Stolen token without the device key

Defence in protocol v1
A token alone is not enough: every request also needs a fresh signature from the device's private key, and replayed proofs are refused.
Residual risk
A thief who also holds the device key is the stolen-device case below.
4

Stolen or lost device

Defence in protocol v1
Device-bound tokens; revoked sessions and devices are checked on every request and fail closed. Removing a device requires a rekey before new writes.
Residual risk
Values already decrypted on that device stay exposed. Rotate them.
5

Removed member of a shared vault

Defence in protocol v1
Removal moves the vault to a new key epoch wrapped only to the remaining members, and affected items are marked to rotate.
Residual risk
Values they already saw cannot be clawed back.
6

Stale or conflicting devices

Defence in protocol v1
Revision compare-and-swap with preserved conflict branches, idempotent writes and tombstones. An offline device cannot resurrect a deleted secret.
Residual risk
Conflicts need an explicit decision from you.
7

Hostile shared metadata (prompt injection)

Defence in protocol v1
Descriptions, URLs and profiles are untrusted, author-attributed data and never instructions. Portable policy can only narrow local grants. High-sensitivity secrets always need fresh approval.
Residual risk
An agent you grant a secret to receives its plaintext.
Guarantees and limitations

Design properties, side by side with what they cannot do.

These are design properties of protocol v1 as proposed, not reviewed results.

Design guarantees

as proposed
  • No custom cryptography. XChaCha20-Poly1305, Ed25519, X25519, HKDF-SHA256 and Argon2id from audited libraries. Unknown algorithm IDs fail closed. spec §1
  • Cross-language test vectors. Go and TypeScript must reproduce every vector byte for byte, including the rejection cases.
  • Local-first. resolve never depends on the network; with sync off, secrets make zero network requests.
  • Recovery without trusting the server. The recovery bundle carries the owner's public trust anchor, the recovery signing key and the newest witnessed checkpoint, so a fresh device does not take the server's word. spec §3.4
  • Encrypted, chained audit. Reordering, dropping or overwriting audit entries since a witnessed checkpoint is detected. spec §7
  • Least-privilege authorization. Token scope intersected with vault membership; readers and machine identities are read-only at the Worker; no cross-vault access. spec §9

Known limitations

stays your risk
  • Vault-wide key. A vault key decrypts every item in that vault. v1 makes no per-secret access claim; use separate vaults. spec §3
  • Freeze attack. Updates a device never witnessed can be withheld. Detection needs a second channel; transparency logs and gossip are out of scope for v1. spec §6
  • Plaintext to the child process. ak secrets run (planned) releases the value to the approved process by design.
  • No claw-back. Removing a device or member protects only new material. Anything already decrypted stays exposed; affected items are marked to rotate.
  • Visible metadata. Random IDs, revisions, sizes, timestamps, device public keys, roles and request metadata.
  • Compromised local client. Malware running as you, or a modified ak, sees plaintext and keys. The protocol does not defend the endpoint.
  • Key loss is final. Lose every enrolled device, the master password and the recovery key, and nobody can decrypt the vault.
  • Audit entries are not signed per author. Any device that held a key epoch can write audit entries at that epoch, including one removed later, until the rekeying device appends at the new epoch. spec §7
  • Roles are enforced by the Worker. Clients do not yet check records against role history, so read-only roles and machine identities rely on the Worker (#22).
  • Removal fence binds the log its remover verified. A device that reads the log later detects records substituted at or below the fence, but records the removed device wrote before its removal stay valid. A device that keeps writing can stall its own removal, so revoke it first. (spec §5)
  • Older betas lack the removal fence. ak releases up to v3.0.0-beta.30 neither sign nor check removal fences, so they cannot remove a device or recover, and they do not get the fence check above. Upgrade to v3.0.0-beta.31 or later, which includes the fence client, or revoke a lost device in your AgentKit account (agentkit#2469).
  • Operators can see proofs in the live log tail. Account members with Workers Tail access see request proofs and webhook signatures in the live tail. Each is single-use and bound to one request; tokens are redacted (#61).
  • No independent third-party review. By owner decision the GA security review is performed by the project owner and is still pending; the owner directs the agents that built ak-vault. No reviewer outside the project has reviewed it (#8).
  • Recovery bundle can be guessed offline. Anyone with a live owner-account session can download the encrypted bundle and guess a weak password offline. Revoke your sessions after a loss. spec §3.4
  • Trust on first use at genesis. The owner's key is pinned on first use unless it arrives through the recovery bundle or a SAS-verified pairing. spec §4
Release gate

What must be true before general availability

A box counts only when its evidence is linked on issue #8 for the exact commit being released. The full list lives in the release gates.

  • Gate items; status and evidence are in the release gatessync not GA
  • ADR 0001 approved by the owner, with its open items resolved.
  • Go and TypeScript reproduce every test vector byte for byte, including every rejection vector.
  • The Worker integration suite is green: conflicts, tombstones, idempotency, cross-tenant denial, replayed proofs, revoked devices and stale membership.
  • Disclosure scan: storage dumps, logs, traces, metrics and error responses from a seeded run contain no planted plaintext values or names. The live log tail shows request proofs and webhook signatures to account operators; the owner accepted that (#61).
  • A revoked session or device is refused on its next request, even with an unexpired token.
  • With sync off, ak makes zero HTTP requests and resolve works with the Worker unreachable.
  • Red-team scenarios executed (13 waits for the feature it attacks), a two-device end-to-end run with real clients, and backup, restore and rollback rehearsed on staging.
  • The removal fence binds the change-log contents, not only a position.
  • The project owner reviews and signs off on #8 personally. This is not an independent third-party review, and agents cannot post or attest it.
