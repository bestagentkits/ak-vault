Protocol v1 · in security review

How a secret stays sealed from one device to the next.

A walkthrough of protocol v1 as proposed: the keys, how a new device joins, how conflicting edits are kept, and how devices notice a server that lies about history. Where this page simplifies, the normative spec wins.

KeysEnrollmentConflictsDeletes and rollbackArchitectureWhat the server sees
Keys

Three ways to open a vault. The server holds none of them.

Each vault has one random vault key, and every item gets its own key derived from it. The server stores the vault key only in wrapped form, locked to things only you hold.

  • Each enrolled device. The vault key is wrapped to the device's X25519 key, so only that device can unwrap its copy.
  • Your master password. Stretched with Argon2id, so a stolen wrapped copy has to be guessed offline.
  • Your recovery key. 32 random bytes shown in groups of characters, for when every device is gone.
  • One key opens the whole vault. Any member device can decrypt every item. Separate vaults are the only access boundary.
Enrollment

A new device joins only after you compare six digits.

The server relays enrollment messages, so it could try to slip in a key of its own. A short authentication string (SAS) stops that.

  1. The new device creates its keys

    It generates its own signing and key-exchange keys. The private halves never leave it.

  2. Both screens show a code

    Each device hashes the same transcript and shows six digits.

  3. You compare, then approve

    If the codes match, the owner device signs a device_add event that commits to the enrollment transcript and to the vault key wrapped for the new device. If they differ, enrollment aborts.

  4. The new device verifies first

    It checks the signed member list and wrap set against the owner's signature before it unwraps anything.

The protocol defines this flow; the enrollment experience in ak is a hidden preview in the released CLI, not yet a supported workflow. If every device is lost, a fresh device can enroll itself with your password or recovery key through the encrypted recovery bundle.

Conflicts

Two edits, one secret. Neither one is lost.

Many sync tools keep whichever write lands last. ak-vault never does. Every write names the revision it started from, and the server accepts it only if that is still the current revision.

Deletes and rollback

Deleted stays deleted. Old state stays old.

A server, or a device that slept for a month, should not be able to bring back history you moved past.

Limitation: withheld updates. A malicious server can still hide updates from a device that has never seen them, such as a new or long-offline device. Detecting that needs a second channel, like another device's checkpoint or the recovery bundle. Transparency logs are out of scope for v1.

Architecture

Small server, strong clients.

All encryption, decryption and signing of vault data happens in clients, using audited libraries. The server verifies tokens and request signatures, orders writes and stores ciphertext. There is no custom cryptography anywhere.

What the server sees

A short, explicit list of what leaves your device.

The Worker and its per-vault storage hold ciphertext and the metadata needed to order, authorize and rate-limit writes. The data classification owns the full list.
